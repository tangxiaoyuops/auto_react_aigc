## 1. 现状盘点（2026-09-24 核实）

### 1.1 已经具备的地基（好消息）

后端**控制平面（control-plane）**已经构建了通用的"资源库 + 外键挂载"骨架，这正是"可配置"的核心底座：

| 层 | 现状 | 关键代码 |
|---|---|---|
| **统一资源模型** | `DBResource` 一张表承载 5 类资源：`kb / skill / prompt / ontology / ds`，`meta` JSON 兜底任意字段 | `shared/schemas/resource.py`、`control-plane/.../resource_service.py` |
| **资源 CRUD API** | `/resources?type=...` 支持 5 类资源增删改查、按类型过滤 | `control-plane/.../routes/resources.py` |
| **Agent 模型** | `Agent` 通过 `knowledge_ids / skill_ids / ontology_ids` **外键指针**关联资源 | `shared/schemas/agent.py` |
| **Agent CRUD + 状态机** | 创建/更新/上架/下架，上架打版本快照 | `agent_service.py` 的 `transition_status` |
| **能力挂载 API** | `POST /agents/{id}/capabilities` 挂载知识库/本体/Skill | `routes/agents.py` |
| **工具注册表（认知层）** | Cordis 风格 `@tool` 装饰器 + 全局 `inventory`，自描述、自动生成 schema | `cognition-plane/app/tools/base.py` |

### 1.2 三大断链（真正的缺口）

| # | 断链 | 具体表现 |
|---|---|---|
| **断链 1** | **前端拿的是 Mock，不是后端 API** | `frontend/src/pages/resources/index.tsx` 用的 `KNOWLEDGE_POOL / SKILL_POOL / ONTOLOGY_POOL`（`mock/agents.ts` 静态数据）；「新建」按钮是 `alert()`。后端 `/resources` API 前端根本没调用 |
| **断链 2** | **`cognition-plane/app/skills` 目录是空的** | Skill 在运行时没有载体——只是标签，Agent 运行时不加载、不执行 skill |
| **断链 3** | **prompt 未资源化，与 Agent 内联字段割裂** | `Agent.system_prompt` 直接内联存 Agent 上，`type=prompt` 资源库是另一套，gathered连同 |

> **结论**：后端"可配置"地基已 80% 就位；真正要做的是 **前端对接真实 API + 认知层 skill/prompt 运行时落地 + 资源与 Agent 打通**。

## 2. 目标架构：统一的"资源 + 能力 + 运行时"模型

### 2.1 六类资源统一模型

保留现有 `Resource` 表结构，但为每类定义 **标准 `meta` 规范**，让前端可表单化配置：

| 类型 key | 名称 | `meta` 标准字段 |
|---|---|---|
| `tool` | 工具 | `{ name, display_name, category, input_schema, enabled }` |
| `skill` | Skill | `{ version, steps[], tools[], prompt_template }` |
| `prompt` | 提示词 | `{ version, template, variables[], tags[] }` |
| `kb` | 知识库 | `{ docs, retriever, index_status }` |
| `ontology` | 本体 | `{ version, concepts }` |
| `ds` | 数据源 | `{ type, conn, sync_status }` |

> `tool` 新增为第 6 类资源（后端 `RESOURCE_TYPES` 增加 `"tool"`），统一纳入资源池，避免与认知层的 `@tool` 运行时脱节。

### 2.2 三层职责

```
┌─────────────────────────────────────────────────┐
│  Frontend（React）                                │
│  ─ 六类可配置表单 / 资源库 / Agent 配置 / Debug     │
│  ─ 全部调用真实 REST API（不再读 mock 池）          │
└──────────────────────┬──────────────────────┘
                       │ REST /agents /resources
┌──────────────────────▼──────────────────────┐
│  Control Plane（控制层：配置态）                 │
│  ─ Resource 统一 CRUD（6 类）                 │
│  ─ Agent 配置 + 能力挂载                      │
│  ─ 运行前「装配」：把 Agent+资源 编译为 RunSpec   │
└──────────────────────┬──────────────────────┘
                       │ RunSpec (json)
┌──────────────────────▼──────────────────────┐
│  Cognition Plane（认知层：运行时）              │
│  ─ Skill 注册表 + 动态装载                    │
│  ─ Tool 注册表（已有 @tool + inventory）      │
│  ─ Prompt 模板渲染 → system prompt           │
│  ─ ReAct 图（现有 LangGraph engine）           │
└─────────────────────────────────────────────┘
```

### 2.3 装配（Compile）流程 —— 关键新概念

配置态（Control Plane 存的是**资源 ID 引用**）运行态（Cognition Plane 需要的是**可执行数据**）之间需要一个**装配器**：

```
RunSpec = compile(agent, resources) {
  system_prompt = render(prompt_template, variables)
                + concat(skill.prompt_template for skill in agent.skill_ids)
  tools        = [tool for tool in agent.tools_ids]        # schema 从认知层 inventory 取
  tools        += [skill.load_tools()]                     # skill 携带的工具
  knowledge    = resolve(agent.knowledge_ids)             # kb 检索参数
  model        = agent.model
}
```

运行时改造成立的关键：**Cognition Plane 支持按 `RunSpec` 动态装配**，而不是全局 `_build_tool_schemas()` 一次性绑定所有工具。

## 4. 风险与注意点

1. **认知层与配置层的工具 schema 一致性**：`Resource(tool)` 的 `meta` 与认知层 `inventory` 的 `ToolDef` 必须对齐，建议由控制平面 `compile_runspec` 时**从认知层拉取真实 schema**，资源表只存展示态。
2. **skill 的 prompt 与主 prompt**：合并时注意先后顺序（主 prompt → skill 段 → 工具说明），给出可配置的 `insert_position`。
3. **向后兼容**：`system_prompt` 内联字段保留，新增 `prompt_resource_id` 为可选项，避免破坏已有 Agent。
4. **mock 回退策略**：前端 store 沿用 `agentStore` 的「后端不可达回退本地」模式，保证离线调试链路不断。
